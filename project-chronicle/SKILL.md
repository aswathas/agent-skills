# Project Chronicle

Maintain a complete, readable record of how a project was actually built —
including the parts that failed.

You are producing two things at once: a record a stranger can read in ten
minutes and understand the project, and a git history with real granularity.
Neither is a side effect of the other. Every commit you make must correspond to
a change someone would want to read about.

## Ground rules

**Only ever touch paths under `docs/`.** This skill never stages or commits
source code, config, or lockfiles. It commits its own documentation and nothing
else.

**Never amend, never squash, never rebase away history.** Squashed commits are
invisible to the GitHub contribution graph and collapse the reasoning this skill
exists to preserve. If a commit was wrong, add a new one that corrects it.

**Never invent a beat.** If the user has not stated a problem, do not write
`01-problem.md` with a guess. Ask. An honest gap in the docs beats a plausible
fiction in a document whose entire purpose is to be trusted.

**Skip ahead when the beat already happened.** Do not force the user through
beats 1-3 in order. Someone starting mid-project with a problem and a decision
already made needs `02-options.md` and `03-decision.md`, not a full interview.

## When to engage

Start a chronicle when the user describes a new project, a feature with real
uncertainty, or a decision that will be expensive to revisit later.

Write to the chronicle when the user states or changes a decision, abandons an
approach, freezes scope, or completes a verification run.

**Do not** engage for routine bug fixes, typo edits, dependency bumps, or
anything a commit message alone explains.

## Structure

```
docs/
  01-problem.md
  02-options.md
  03-decision.md
  04-plan.md
  05-mvp.md
  06-verification.md
  07-retro.md
  attempts/
    001-<slug>.md
    002-<slug>.md
  decisions/
    NNN-<slug>.md
```

Numbering is fixed. A reader must be able to `ls docs/` and know the story
order without opening anything.

## The seven beats

### 1. `01-problem.md` — the problem

Written once, at kickoff, from what the user actually said.

Must answer: what breaks or is missing, for whom, what it costs them today,
and what happens if it is never fixed. If the user cannot state the cost, that
is the thing to establish before anything else.

### 2. `02-options.md` — the options

Every approach considered, including the ones dismissed early and the ones the
user never seriously entertained. For each: the shape of it and the reason it
was or was not viable.

This file is not a list of one. A record with a single option is a decision
record wearing the wrong hat, and it hides the fact that a real choice was made.

### 3. `03-decision.md` — the decision

What was chosen, and — the part that matters — what specifically ruled out each
other option. "Option B was slower" is weak. "Option B requires a migration
step we cannot run against production data before launch" is a decision someone
can revisit in six months.

Also record what would change the decision. Conditions that would reopen it.

### 4. `04-plan.md` — the plan

The phases, in order, with what each phase delivers. This is the commit that
says scope is locked.

Once written, do not edit this file to change the plan. Write a file in
`decisions/` recording the change and reference it from the plan. The history of
changing your mind is the most valuable thing in the whole directory.

### 5. `05-mvp.md` — MVP scope

Two explicit lists: what the MVP does, and what it deliberately does not. Every
exclusion gets a reason — "no auth in v1" is a decision; "no auth" is an
oversight. The excluded list is what stops the next person re-adding it.

### 6. `06-verification.md` — verification

What was tested, what passed, what failed, and what is still untested. Record
failures with the same care as passes. A verification file that only lists green
checkmarks is not a verification record.

### 7. `07-retro.md` — retro

What we would do differently, what we would keep, and what the next iteration
should start with. Written after the MVP is real, not before.

## `attempts/` — the failed paths

The part that makes this worth keeping. One file per attempt at a solution,
numbered from 001, append-only.

Open the file when an attempt starts. Close it when it ships or dies.

```markdown
# Attempt 001 — Postgres schema

**Hypothesis.** Normalized relational schema avoids the fan-out we hit on reads.

**How we tested it.** Built the schema, seeded 10k rows, measured p95 read.

**What actually happened.** p95 was 40ms on a 4-column join and 900ms on the
audit join. The audit path is the hot one, and relational made it worse.

**Outcome.** Abandoned.

**Why we moved on.** We need wide reads far more than we need write integrity,
and every fix for the join problem added a cache layer we would now have to
invalidate anyway.
```

An abandoned attempt gets **two** commits: one when opened, one when written
up as abandoned. The failure is the most valuable thing in the directory — it
is what stops the next person, or you in eight months, from trying the same
thing.

When an attempt is abandoned, also append a line to `03-decision.md` recording
the change. Do not rewrite the decision; supersede it.

## `decisions/` — scope and plan changes

One file per change to a locked beat. `NNN-<slug>.md`, numbered from 001.

```markdown
# 001 — Drop live search from v1

**Date.** 2026-10-15
**Supersedes.** Beat 4, phase 3.
**Change.** Live search moved out of v1 into v2.
**Why.** The index rebuild is 4 minutes on the current dataset size. That is
untenable on every deploy. Deferred, not rejected.
```

Do not edit the superseded beat. Link to the new file from it.

## Commit rules

Commit each file the moment it is written. No batching at project end.

| What | Message |
|---|---|
| New beat | `docs: state problem` / `docs: record options considered` / `docs: decide on <X>` |
| Plan locked | `docs: lock plan, <N> phases` |
| MVP frozen | `docs: define MVP scope` |
| Verification | `docs: record verification, <N>/<M> passing` |
| Retro | `docs: retro` |
| Attempt opened | `docs: open attempt NNN, <hypothesis>` |
| Attempt closed as failed | `docs: abandon attempt NNN, <why>` |
| Attempt closed as shipped | `docs: attempt NNN shipped` |
| Decision change | `docs: change NNN, <what>` |

Commit silently. Do not ask for confirmation on the message. Do not amend a
commit you already made — if the file was wrong, fix the file and commit again.

Before the first commit in a directory, check `docs/01-problem.md` does not
already exist. If it does, this is an existing project — read what is there,
find the beat that matches what the user just did, and continue rather than
starting over.

## Writing the files

Prose, not bullet soup. A sentence that says why beats a list of nouns.

- Address the reader as someone who has not seen any of this before.
- Every claim about a past decision traces to something the user actually said.
- Quote the user's own words for the problem statement. Do not polish a
  complaint into a specification and present it as their requirement.
- If a section would be empty because the beat has not happened, leave the file
  unwritten.

## Diátaxis — what type each beat is

A chronicle is a mixture, and knowing which mixture matters because each beat has
a different reader arriving with a different question.

| Beat | Type | The reader is asking |
|---|---|---|
| `01-problem` | Explanation | Why was this worth doing? |
| `02-options` | Explanation | What else was possible, and why not? |
| `03-decision` | Explanation | Why this, and what would reopen it? |
| `04-plan` | Reference | What happens, in what order? |
| `05-mvp` | Reference | What does it do, and what does it deliberately not? |
| `06-verification` | Reference | What was actually measured? |
| `07-retro` | Explanation | What would we do differently? |
| `attempts/` | Explanation | What happened, and why did it fail? |
| `decisions/` | Reference | What changed, superseding what? |

**A chronicle is never a tutorial.** Do not turn these files into lessons. A
tutorial walks a newcomer through a successful outcome; these files exist to
explain a specific project that already happened, including where it went wrong.
The temptation is to write `04-plan.md` as step-by-step instructions — resist it.
It is a record of what was done and in what order, not instructions someone
should follow.

**A chronicle is never a how-to guide.** Do not add a numbered procedure for
reproducing the work. The project's own README owns that; a chronicle that starts
answering "how do I run this" is competing with it and will go stale differently.

Three principles carry over from the framework and are worth stating because they
are easy to get wrong here:

- **Clarity** — say what happened before saying why it mattered. A reader who has
  not seen any of this should not have to reconstruct the sequence from prose
  ordering alone.
- **Accuracy** — a claim about a past decision traces to something the user
  actually said. This is already a ground rule above; it is restated here because
  it is the principle most often violated in the name of good prose.
- **User-centricity** — write for the reader of that specific beat. `01-problem`
  is read by someone deciding whether this project is worth their time;
  `06-verification` is read by someone deciding whether to trust it. Same project,
  different question, different opening.

### What is deliberately not imported

The Diátaxis workflow asks you to clarify the audience and goal, propose an
outline, and wait for approval before writing. That contradicts this skill's
ground rules: a beat is written the moment it happens and committed silently, and
a decision made six months ago cannot wait for someone to approve an outline.

Take the type system and the writing principles. Leave the approval gate. A
chronicle that stops to ask permission is a chronicle that never finishes
recording the thing it exists to record.

When the two genuinely conflict — the reader's question is ambiguous — resolve it
by writing for the reader named in the table above rather than by asking.
